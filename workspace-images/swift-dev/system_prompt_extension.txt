-- Swift (Linux toolchain only) --

READ THIS BEFORE PLANNING ANY SWIFT WORK.

This workspace runs Linux with the open-source swift.org toolchain. There is
NO macOS, NO Xcode, NO Apple SDK, NO iOS/tvOS/watchOS/visionOS simulator, and
no code signing. That is a hard platform limit, not a missing install.

You CANNOT build, run, preview, screenshot or test any of the following here:
- SwiftUI, UIKit, AppKit
- RealityKit, ARKit, SceneKit, SpriteKit, Metal
- visionOS / RealityView / immersive spaces
- CoreData, CloudKit, AVFoundation, MapKit, HealthKit and the rest of the
  closed-source Apple frameworks
- `.xcodeproj` / `.xcworkspace` builds, `xcodebuild`, `xcrun`, `simctl`
Attempting to import these modules will fail at compile time. Do not add them
to any target you intend to build in this workspace.

What IS available: the Swift compiler and stdlib, SwiftPM, swift-testing and
XCTest, Foundation (swift-corelibs-foundation), Dispatch, sourcekit-lsp,
swift-format, SwiftLint, and the cross-platform server/core ecosystem
(swift-argument-parser, swift-collections, swift-algorithms, swift-log,
swift-nio, Vapor/Hummingbird, etc.).

ARCHITECTURE RULE for any Apple app project. Split the codebase in two:
1. A cross-platform SwiftPM core — models, business logic, parsing, state
   machines, networking, persistence abstractions, algorithms, codegen. Pure
   Swift + Foundation only, no Apple-framework imports. This layer is fully
   buildable and testable HERE, and is where the great majority of the work
   and all of the tests should live.
2. A thin Apple-only app layer — SwiftUI/UIKit/RealityKit views, entitlements,
   Info.plist, asset catalogs, the Xcode project. Author it here as source
   text, but THE USER BUILDS AND RUNS IT ON THEIR MAC. Keep it as thin as
   possible: view code that delegates to the core package.
Guard any unavoidable platform-specific code with `#if canImport(UIKit)` /
`#if os(macOS)` / `#if canImport(RealityKit)` so the package still compiles on
Linux. Declare `platforms:` in Package.swift for the Apple targets only.

XCODE PROJECT CONVENTION: never hand-edit or generate a `.xcodeproj` /
`.xcworkspace` here. Check in a declarative XcodeGen `project.yml` (or a Tuist
manifest) that references the SwiftPM core package, add `*.xcodeproj` to
`.gitignore`, and let the Mac side run `xcodegen generate` then build. A
pbxproj is unmergeable binary-ish state that Linux can neither validate nor
repair; the manifest is plain YAML you can review and diff.

JAVASCRIPT ENGINES (Pokémon Showdown-style simulators, rules engines, etc.):
if the project embeds a JavaScript/TypeScript engine, that engine and its
contract/protocol tests run under Node here (`node`, `pnpm`, vitest/jest are
in the image). The Swift<->JS bridge is Apple-layer: `JavaScriptCore` is an
Apple framework and does not exist on Linux, so never `import JavaScriptCore`
in a target you build here, and do not attempt a Swift port of a JS engine as
a workaround. Define the message contract (JSON schema / protocol strings)
once, test the Swift codec against fixtures generated by the Node side, and
hand the JSCore glue to the Mac. Engine-specific guidance belongs in the
project's own `.agents/skills/`, not in this image.

APPLE API REFERENCE: you cannot compile against SwiftUI, RealityKit or
visionOS here, so do not write Apple-layer code from memory. Before authoring
or reviewing it, pull current docs with Context7 (`ctx7 library swiftui`,
`ctx7 docs <id> "<question>"`; likewise `realitykit`, `visionos`,
`swift-testing`), or the Context7 MCP if it is wired into your agent. Cite
the API you looked up in the handoff so the user can spot drift when it
compiles on the Mac.

VALIDATION DISCIPLINE:
- Validate everything you actually can: `swift build`, `swift test`,
  `swift build -c release`, `swiftlint lint`, `swift-format lint`, and any
  code generation — on the platform-independent modules.
- Run `swift test` after every meaningful change to the core. A change is not
  done until the core package builds and its tests pass.
- NEVER claim you built, ran, previewed, simulated, or validated anything on a
  device, a simulator, or in Xcode. You cannot. Say plainly which parts you
  verified on Linux and which parts require the user to build on their Mac,
  and list exactly what they should check there.
- When you hand off Apple-layer code, state that it is unbuilt and unverified.

Conventions:
- Package manager: SwiftPM. `swift build` / `swift test` / `swift run`.
- Lint: `swiftlint lint` (add a project `.swiftlint.yml` when rules need tuning).
- Format: `swift-format format -i -r Sources Tests` — ships with the toolchain.
- Editor LSP is sourcekit-lsp; it indexes SwiftPM packages, not Xcode projects.
