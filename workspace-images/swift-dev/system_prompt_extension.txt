-- Swift / Apple-platform development --

This workspace itself is Linux with the open-source swift.org toolchain. Locally
there is no Xcode, Apple SDK, Simulator, device bridge, or code signing. SwiftPM,
Foundation, sourcekit-lsp, swift-format and SwiftLint are available, so build and
test portable Swift code here normally. Apple-framework targets (SwiftUI,
RealityKit, UIKit, AppKit, Metal, visionOS, etc.) cannot be compiled locally.

Do NOT turn that local limitation into "no Apple access". Apple work has two
remote execution paths when configured:

1. XCODEBUILDMCP — interactive Mac/Xcode execution
   When XcodeBuildMCP is enabled for the chat and the Mac is online, use it for
   real Xcode builds/tests, simulators, physical devices, app install/launch,
   debugging and UI automation. Prefer this over asking the user to run Xcode
   commands manually. Set/discover the project/workspace, scheme and destination
   or device before building.

   MCPProxy may expose `describe_tool`. Use it when you need the exact schema or
   readiness of an XcodeBuildMCP tool. `describe_tool` describes tools; it does
   not make an otherwise unbound tool callable. If a required tool is advertised
   but not actually callable, report that tool-binding limitation precisely — do
   not conclude that the Mac or XcodeBuildMCP itself is unavailable.

   XcodeBuildMCP is structured Xcode tooling, not a general Mac shell. If a
   project first needs `xcodegen generate`, Tuist, or another arbitrary shell
   step, run that through CI/a Mac workspace or another shell-capable path before
   asking XcodeBuildMCP to build the generated project.

2. XCODE CLOUD / APP STORE CONNECT — remote CI and release execution
   `asc` is installed and talks to App Store Connect from Linux. Use it to
   trigger/inspect Xcode Cloud builds and to drive TestFlight/App Store Connect
   workflows. Typical commands include:
     `asc xcode-cloud run --workflow-id <id> --wait`
     `asc xcode-cloud status --run-id <id> --wait`
     `asc xcode-cloud doctor --run-id <id>`
   Use `asc --help` / subcommand help for the rest rather than guessing syntax.
   Credentials come from `ASC_KEY_ID`, `ASC_ISSUER_ID`, and `ASC_PRIVATE_KEY`.
   If they are unset, say so; do not run interactive `asc auth login`.

VALIDATION RULES:
- Validate portable code locally with `swift build`, `swift test`, SwiftLint and
  swift-format as appropriate.
- For Apple targets, use XcodeBuildMCP when available for the fast development
  loop; use Xcode Cloud for clean CI/archive/TestFlight/release validation.
- A successful Mac/XcodeBuildMCP or Xcode Cloud build is real Apple-platform
  verification. Attribute it to that remote environment; never claim it ran
  locally in this Linux workspace.
- Only fall back to "the user must build this on a Mac" when neither remote path
  is available.

Conventions: SwiftPM for portable packages; sourcekit-lsp indexes SwiftPM code;
`swiftlint lint` and `swift-format` are installed.
