# Pokémon Showdown simulation from a Swift project

The Pokémon Showdown battle engine is TypeScript. The `@pkmn/*` packages
are the maintained, typed extraction of it and are the right dependency
for a native app; do not port the engine to Swift. Node 20 + pnpm are in
this image, so everything on the JS side is fully runnable and testable
here. The only part that is not is the Swift<->JavaScriptCore glue, which
is Apple-layer and gets built on the user's Mac.

## Packages (verified on npm 2026-09-12)

| Package | What it is | Use it for |
|---|---|---|
| `@pkmn/sim` | The simulator (`sim/` of smogon/pokemon-showdown), typed, browser-safe | Running battles, validating teams |
| `@pkmn/dex` | Unified data layer (species, moves, items, abilities, learnsets, types) | Static data queries, without the engine |
| `@pkmn/data` | Client-flavoured data layer built on `@pkmn/dex` | Display-oriented lookups |
| `@pkmn/protocol` | Parser for `PROTOCOL.md` / `SIM-PROTOCOL.md` messages | Turning `|move|`, `|-damage|`… lines into typed events |
| `@pkmn/client` | Client battle state engine built on `@pkmn/protocol` | Reconstructing what a player sees from the protocol stream |
| `@pkmn/randoms` | Random-battle team generators | `Teams.setGeneratorFactory(TeamGenerators)` before `Teams.generate` |
| `@pkmn/sets` | Team / set parsing and packing | Import/export of teams; prefer it over `Teams` when generation matters |
| `@pkmn/img` | Sprite/icon URL logic | Only if you reuse Showdown artwork |

`pokemon-showdown` (the full server) is the alternative when you need the
whole thing vendored; for an embedded engine `@pkmn/sim` is smaller and
type-checks externally.

## Canonical driver (Node)

```ts
import {Dex, BattleStreams, RandomPlayerAI, Teams} from '@pkmn/sim';
import {TeamGenerators} from '@pkmn/randoms';

Teams.setGeneratorFactory(TeamGenerators);

const streams = BattleStreams.getPlayerStreams(new BattleStreams.BattleStream());
const spec = {formatid: 'gen9customgame'};
const p1spec = {name: 'P1', team: Teams.pack(Teams.generate('gen9randombattle'))};
const p2spec = {name: 'P2', team: Teams.pack(Teams.generate('gen9randombattle'))};

void new RandomPlayerAI(streams.p1).start();
void new RandomPlayerAI(streams.p2).start();

void (async () => {
  for await (const chunk of streams.omniscient) console.log(chunk);
})();

void streams.omniscient.write(`>start ${JSON.stringify(spec)}
>player p1 ${JSON.stringify(p1spec)}
>player p2 ${JSON.stringify(p2spec)}`);
```

Input is line-oriented SIM-PROTOCOL (`>start`, `>player`, `>p1 move 1`);
output is line-oriented PROTOCOL (`|turn|1`, `|move|p1a: ...`). Both are
plain strings, which is exactly why the engine embeds cleanly behind a
narrow bridge.

## Architecture for a Swift app

Keep three layers and test each where it can be tested:

1. **Engine bundle (JS, tested here).** Bundle `@pkmn/sim` (+ `randoms`,
   `protocol` as needed) into one ES5/ES2020 script with esbuild or
   rollup, exposing a tiny surface: `createBattle(spec)`, `write(line)`,
   and an `onOutput(line)` callback. No Node APIs (no `fs`, `process`,
   streams) in the exposed surface; JavaScriptCore has none of them.
   Test it with vitest under Node using the same bundle the app will ship.
2. **Contract (shared, tested here).** The protocol lines are the
   contract. Commit fixture transcripts generated by the Node side
   (`fixtures/*.log`) and test the Swift parser/codec against them in the
   cross-platform SwiftPM core (`swift test`). Prefer `@pkmn/protocol`'s
   typed events as the reference for what the Swift model must represent.
3. **Bridge (Apple-layer, built on the Mac).** A thin `JSContext` wrapper
   that loads the bundle, calls the exposed functions, and forwards
   output lines to the Swift core. Guard with `#if canImport(JavaScriptCore)`.
   Hand it off as unbuilt and unverified; list what to check in Xcode
   (bundle loads, one full random battle completes, no main-thread stalls).

Never `import JavaScriptCore` in a target you `swift build` on Linux, and
never ship the Node driver above as the app's engine - the app uses the
bundled script, not `node`.

## Gotchas

- `Teams.generate` throws until `Teams.setGeneratorFactory(TeamGenerators)`
  has been called; `@pkmn/sim` ships no random-battle data of its own.
- `@pkmn/sim` bundles only stable, mod-free formats; custom formats are
  supplied by the caller, not pulled from Showdown's `config/formats.ts`.
- Gens 1-9 only; `Dex.forGen` / `Dex.mod` throw on anything else.
- All generation data loads eagerly; there is no lazy `includeX` dance,
  but the bundle is correspondingly large - measure it before shipping.
- `@pkmn/sim` `Dex` types are looser than `@pkmn/dex-types`; cast when
  crossing between them.
- Pin the `@pkmn/*` versions together (they release in lockstep for
  `sim`/`dex`/`data`/`randoms`); mixing versions breaks data agreement.
